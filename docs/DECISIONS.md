## 1. 保留哪些模块、走哪条部署路线

**结论**：只保留收件、查询、详情、删除、到期清理、静态网页；唯一部署路线是 Cloudflare 控制台的 Workers Git 集成（Import a repository）。

保留清单（每个都能对应一条需求）：

| 文件 | 职责 | 对应需求 |
| --- | --- | --- |
| `src/inbound.js` | MIME 解析、入库、内嵌图片落库 | 第 4 步收信保存 |
| `src/extract.js` | 验证码提取 | 查询时返回验证码 |
| `src/db.js` | D1 建表与查询、过期清理 | 24 小时保留、自动清理 |
| `src/api.js` | 四个接口 + 图片读取 | 四类接口 |
| `src/html.js` | 清洗、转文本、cid 改写 | 查看原文、正文图片 |
| `public/index.html` | 单页界面 | 网页设计建议全表 |
| `src/index.js` | 三个 handler 的入口 | 路由与定时任务 |

删除并确认无残留：发件（Resend / Cloudflare SendEmail）、站内转发、Telegram、Webhook、通讯录、多用户与角色权限、注册密钥、统计与图表、OAuth 登录、JWT、KV 设置缓存、R2/S3 存储适配、Vue 前端与构建产物、GitHub Actions 工作流、`/api/init` 初始化接口、管理员注册。

**为什么不走 GitHub Actions**：上游工作流需要账号级 `CLOUDFLARE_API_TOKEN`（含 D1、KV、R2 编辑权限）写进仓库 Secrets，还要把初始化密钥拼进 `GET /api/init/{secret}` 的 URL，这个 URL 会留在 Actions 日志里。本项目不需要发信、不需要令牌，走 Git 集成可以让 Cloudflare 自己管令牌，仓库里没有任何密钥。

**为什么不两条都写**：两条路线的初始化方式、必填项、失败模式都不同，叠加会让人分不清哪步必须做。文档只写一条，另一条在 README 的差异表里说明为什么不用。

> 依据：源码核查（读 `deploy-cloudflare.yml`、`init.js`、`wrangler.toml`）+ 官方文档核查（Workers Builds 自动安装依赖、Build command 可留空）。

## 2. 程序取哪封邮件、接口返回什么

**结论**：列表支持三种范围参数，全部由调用方决定，服务端不建立等待任务。

- `since=<毫秒>`：只返回接收时间不早于该时刻的邮件 —— 对应"本次发码起点"。
- `after=<id>`：只返回 id 更大的邮件，按时间正序 —— 对应"继续查新来信"。
- `before=<id>`：翻更早的页。
- 不带范围参数时返回 24 小时内全部，按时间倒序。

**为什么不再加一层"更短的固定时间限制"**：24 小时是保留期，不是验证码有效期；把起点交给调用方，同时把"哪些邮件算本次"的决定权留在真正知道发码时刻的那一端（人点查询的时刻、程序记录的那一毫秒）。服务端硬编码 5 分钟只会在慢投递时误伤。已确认的默认行为见第 5 节。

**返回里必须有的**：每封邮件的 `id`、发件人、主题、接收时间、`code`、是否有正文、图片数、`status`。`code` 为空不等于没收到信，`status: too_large` 表示收到但没存正文。

> 依据：源码核查（上游 `email-api.js` 的列表/新来信分离）+ 本地实测（`since` / `after` 两条路径都有测试）。
> 请求与返回的完整示例见 [API.md](API.md)。

## 3. 验证码怎么提取，上游的 AI 必须保留吗

**结论**：不保留。改为纯规则提取（关键词定位 + 候选打分），不依赖任何模型。

**上游的做法**：`ai-service.js` 调 `env.ai.run('@cf/meta/llama-3.1-8b-instruct-fast')`，要求模型返回 `{"code":"..."}`，超过 8 位或含空格就丢弃，异常时 `return ''`。

**为什么不保留**：

1. 免费额度每天 1 万 Neurons，一封邮件一次调用，额度用尽时静默返回空码 —— 与"收到信但没码"的正常状态无法区分，排障时看不出是额度问题还是真没码。
2. 每封邮件多几百毫秒到几秒延迟，收件路径本来就卡在 10ms CPU 上。
3. 模型输出不稳定，同一封邮件可能这次给码下次给空。

**规则法的判据**：关键词（验证码 / 校验码 / verification code / passcode / OTP…）附近 90 字符内找候选，按"关键词强度 − 距离 + 位数 + 是否在主题"打分，低于阈值返回空。纯数字只接受 4–6 位（7–8 位多半是订单号），年份、优惠码上下文降权。

**边界（必须承认）**：图片里的码、被拆成 `123 456` 的码、引用历史邮件里的旧码都可能取不到或取错。取不到时整封邮件仍然可读，这是需求里明确的出口。

> 依据：源码核查（`ai-service.js`）+ 本地实测（7 个提码用例，含"无验证码"和"年份不误判"两个反例）。

## 4. 图片放哪里，怎样查看与删除

**结论**：存 D1 的独立 `images` 表（BLOB，一行一张图），通过 `/i/{token}/{seq}` 读取，token 随邮件生成。

**为什么不沿用 R2 / S3 / KV**：

- R2 需要先在账号里开启并绑定支付方式，与"免费套餐、谁都能部署"冲突。
- KV 免费额度每天只有 1000 次写入，收几张图就用完。
- S3 要额外账号和密钥，纯属增加部署负担。
- D1 免费 500MB、单行 2MB，单张内嵌图上限 256KB，一封最多 8 张，完全够 24 小时的临时邮件。

**为什么图片地址不需要请求头**：浏览器加载 `<img>` 无法附带 `Authorization`，而邮件正文里的图片必须是普通 `<img>`。所以用随邮件生成的 32 位随机 token 作为能力凭据：只能读这一封的图，邮件删除或过期后 join 查不到记录，地址立即 404。这不是绕过鉴权——正文本身只有持密钥的人能看到，token 只在这封邮件的 HTML 里出现。

**删除与到期**：删信时同一事务批里删 `images`；定时清理先删过期邮件的图片再删邮件；不保留独立永久链接。

> 依据：源码核查（上游 `imgReplace` + `r2-service` 三选一）+ 文档核查（D1 单行 2MB、免费 500MB）+ 本地实测（收图、读图、删信后 404 三条断言）。

## 5. 密钥怎么交给人和程序，网页是否记住

**结论**：一个服务访问密钥，存在 Worker 的 Secret `ACCESS_KEY` 里；网页只存当前标签页（sessionStorage），关闭标签即失效。

- 程序：`Authorization: Bearer <key>` 或 `X-Access-Key`。
- 人：打开网页输入一次，同一标签页后续请求复用，点"退出"清除。
- 仓库、静态页面、示例、日志里都不出现密钥；`wrangler.toml` 只放 `MAIL_DOMAIN`。
- 部署授权（Cloudflare 账号）与邮件访问密钥是两件事，不复用。

**已确认的默认行为**（本次由使用者拍板）：

| 项目 | 结论 |
| --- | --- |
| 取码范围 | 默认返回全部未过期邮件；网页提供"只看新的"开关，打开后只显示开启时刻之后到达的信 |
| 等待节奏 | 每 5 秒查一次，最长 3 分钟，到点停止，可手动继续 |
| 密钥记忆 | 只存当前标签页（sessionStorage），不做"记住此设备" |

**一个细节**：网页计算"只看新的"起点时用服务端 `serverTime` 校正本机时钟；否则本机快几秒就会漏掉刚到的信。

> 依据：本地实测（错误密钥提示、只看新的过滤、退出清除）+ 使用者确认。

## 6. 免费额度不足怎么办，在哪验证

**上限与降级行为**：

| 资源 | 上限 | 触顶时的行为 |
| --- | --- | --- |
| Workers 请求 | 10 万/天 | 返回 Cloudflare 的错误页，网页显示连接失败并停止自动等待 |
| Workers CPU | 10ms/请求 | 超 1 MiB 的邮件不解析，留 `too_large` 占位记录 |
| D1 存储 | 500MB/库 | 写入失败 → `email` handler 抛错，平台按失败处理，日志留痕，不会假装成功 |
| D1 行数写 | 10 万行/天 | 同上 |
| Email Routing | 25MiB/封 | 平台拒收，本地看不到 |
| 单封大小 | 1MiB（本项目设置） | 占位记录 + 网页"超出大小限制" |

D1 500MB 是唯一的硬天花板。按平均一封 30KB 估算约 1.6 万封存量，24 小时清理后日常用量远低于此。
